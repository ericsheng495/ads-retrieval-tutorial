Eight-week study and implementation checklist

Plan for roughly 6–10 hours/week; adjust scope to understanding. The original PDF is preserved. This checklist corrects its leakage wording, baseline formula, and assumptions about guaranteed gains. Each phase ends with a measured result and a short experiment note. Use the reading guide for every named paper below. Start each topic with its concept-first lesson before opening the reference implementation or beginning the checklist.

Week Phases Deliverable
1 0–1 Funnel explanation and a five-epoch reference run
2 1–2 Your own v0, baseline table, and split audit
3 3 Flat/IVF/HNSW benchmark and tradeoff plot
4 4 Controlled negative-sampling ablations

Phase 0 — Understand the funnel

Read: Snap engineering, Covington 2016.

  • [ ] Draw eligibility → candidate generation → heavy models → auction from memory.
  • [ ] Explain what each stage optimizes and why ranking cannot recover a missed candidate.
  • [ ] Write five lines comparing retrieval/ranking objectives, model cost, latency, metrics, failure modes.
  • [ ] Identify scale, freshness, feedback bias, and calibration constraints in the source material.

Done when: give a 60-second explanation and distinguish documented public Snap behavior from assumptions in your learning project.

Phase 1 — Build and understand v0

Read: DSSM, Covington, Koren. Reference code is provided; rebuild it yourself.

  • [ ] Install dependencies and run five epochs on real MovieLens, with a saved log.
  • [ ] Trace positive definition, deduplication, ID remapping, validation/test holdouts.
  • [ ] Explain embedding dimensions, independent towers, dot product, normalization, temperature.
  • [ ] Hand-calculate Recall@K and a three-example multi-positive loss.
  • [ ] Explain unobserved negatives and duplicate-item/known-positive handling.
  • [ ] Sweep temperatures 0.05/0.1/0.2 using validation; record costs and metrics.
  • [ ] Compare against expected random and training-only popularity baselines.

Done when: reproduce the run and explain every step, including any failure to improve or beat popularity. Avoid promising monotonic metrics from five epochs.

Phase 2 — Honest evaluation

Read: BPR, Schnabel, Koren. See the evaluation contract.

  • [ ] Add an unnormalized dot-product MF/BPR or implicit-ALS baseline with its training objective documented.
  • [ ] Use identical candidate pools, splits, K, and seen exclusions for every model.
  • [ ] Assert held-out pairs are absent from that user's training; allow shared items across users.
  • [ ] Compare per-user leave-last-out with a separate global temporal cutoff protocol.
  • [ ] Report head/tail and light/heavy slices from training statistics, with sample sizes.
  • [ ] Isolate items with zero training positives; describe the ID-only limitation.
  • [ ] Append one baseline/results table and investigate the weakest slice.

Done when: one comparable table exists, with a concrete leakage audit and explicit vocabulary/catalog-time assumptions. Per-user chronology alone is insufficient.

Phase 3 — ANN retrieval

Read: Johnson/FAISS, HNSW, ScaNN. Runnable lab.

  • [ ] Export normalized item vectors; match Flat top-K against brute force.
  • [ ] Compare Flat, IVF, and HNSW on identical embeddings and queries.
  • [ ] Sweep nprobe/efSearch, then plot neighbor overlap versus p50/p95 latency.
  • [ ] Report held-out-target recall separately, serial QPS, storage bytes, and memory scope.
  • [ ] Add persisted index metadata and enforce model/index version matching at serving.
  • [ ] Measure scale effects rather than claiming MovieLens proves million-item performance.

Done when: benchmark table/plot and a deliberately mismatched version test exist.

Phase 4 — Negative-sampling improvements

Read: Yi 2019, Yang 2020, Facebook EBR; cross-batch negatives as an extension.

  • [ ] Derive the candidate sampling probability/expected count for your actual sampler.
  • [ ] Implement and ablate logQ correction in training, with the inference rule explained.
  • [ ] Mix uniform corpus and in-batch negatives; document the mixture and its correction.
  • [ ] Mine hard negatives using a checkpoint trained only on training data.
  • [ ] Mask known positives; audit plausible false negatives without claiming to know all of them.
  • [ ] Compare larger batches or a versioned cross-batch queue, including compute/memory costs.
  • [ ] Change one component at a time; rerun head/tail slices and report regressions.

Done when: separate rows isolate each change and you can explain which bias logQ addresses and which exposure biases remain. An improvement is not guaranteed.

Phase 5 — Features and user history

Read: Airbnb embeddings, SASRec; optional PinSage.

  • [ ] Add genre features to the item tower; retain the ID-only ablation.
  • [ ] Build a mean-pooled training-history user tower before attention.
  • [ ] Compare learned pooling with a causal last-N sequential encoder.
  • [ ] Ensure every history is cut off at query time; do not use future interactions.
  • [ ] Compare head/tail/cold items and light/heavy users on identical splits.
  • [ ] Inspect three multi-interest users and explain where a single vector loses coverage.

Done when: an ablation table and concrete qualitative examples explain what features/history helped. A session/history encoder is necessary for unseen OTTO sessions.

Phase 6 — Ads-style eligibility, cold start, freshness

Read: DropoutNet, Facebook EBR, Covington; Snap engineering for ads context.

  • [ ] Define mock category/targeting/budget eligibility using only available query-time data.
  • [ ] Compare pre-filtering with post-filtering plus overfetch; measure eligible recall and latency.
  • [ ] Hold out entire items from training and retrieve them from content features alone.
  • [ ] Give unseen users an explicit popularity/content fallback and test it.
  • [ ] Insert a new item's embedding without rebuilding the whole index; measure time-to-retrievable.
  • [ ] Allocate a small exploration share; measure candidate displacement in simulation.
  • [ ] Persist mappings/manifests and test stale deletions, budget updates, and model changes.

Done when: eligible results, cold users/items, incremental inserts, and mismatch rejection are demonstrated. Offline simulation cannot establish exploration's causal benefit.

Phase 7 — Production and experimentation

Use the Snap post companion and all ten reference lessons for additional ranking and experimentation background. Start with the beginner ranking primer; the architecture track is an extension, not ten required reproductions in one week.

Read: Schnabel, Yi; Snap engineering.

  • [ ] Write one page on offline/online gaps: distribution shift, selection bias, stale vectors.
  • [ ] Draft an A/B hypothesis, randomization unit, success metric, and guardrails.
  • [ ] Choose run duration from power, traffic, delayed labels, and business cycles.
  • [ ] Sketch impression-to-conversion joins, event IDs, observation windows, and late labels.
  • [ ] Explain that popularity/logQ correction does not remove auction/exposure bias.
  • [ ] Predefine ship/iterate/revert rules and monitoring/rollback triggers.

Done when: the written plan makes a falsifiable decision possible. No production traffic or real experiment is required in this tutorial.

Phase 8 — Transfer to OTTO or H&M

Sources: OTTO's official repository, H&M competition.

  • [ ] Choose one dataset, review terms, and create a small reproducible subset first.
  • [ ] Map events, IDs, timestamps, and query histories into a documented data contract.
  • [ ] Adapt the user tower to sessions/history for OTTO; ID-only unseen sessions do not transfer unchanged.
  • [ ] Use a temporal split appropriate to the task and train-only preprocessing.
  • [ ] Re-run popularity/MF and retrieval baselines; document any architecture changes.
  • [ ] Report retrieval Recall@K and, separately, the competition's official metric.
  • [ ] Write one page comparing catalog scale, sparsity, query identity, and cold-start failures.

Done when: one transfer run reproduces from documented commands with honest baselines. OTTO's weighted multi-event Recall@20 and H&M's MAP@12 are not the same metric as our one-target Recall@100. Kaggle scores are optional.

Phase 9 — Onboarding preparation

Read: revisit the papers supporting each choice rather than memorizing titles.

  • [ ] Write a one-page retrieval design covering eligibility, towers, ANN, freshness, and metrics.
  • [ ] Explain recall/latency, dimension/memory, negative sampling, and filtering tradeoffs.
  • [ ] Reproduce results from a fresh environment and collect the final experiment table.
  • [ ] Give a ten-minute design walkthrough and name the largest remaining uncertainty.
  • [ ] Prepare questions: team-owned sources; bottleneck; training/negative sampling; offline-to-online evaluation; index/model freshness and compatibility.

Done when: your explanation is backed by your own measurements, and the repo makes it easy for someone else to reproduce them.
