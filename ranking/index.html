How ranking works: from features to a displayed item

Read the recommender foundations first. Here we build a mental model of a click ranker using one small equation, then connect it to larger models. You do not need to know neural networks to follow the first example.

1. A ranker scores a user, an item, and a situation

A ranker receives a candidate plus its request context. It can estimate the probability of a click, predict watch time, or learn another usefulness score. The product chooses how to use that prediction to order or select candidates.

If you score three candidates as 0.06, 0.04, and 0.12 for click probability, sorting from largest to smallest gives game → boots → coffee in our example. The sorting operation is simple. Learning useful and trustworthy scores is the hard part. A probability score is specific to an event definition and population.

A retrieval dot product is usually a relative similarity score. Its value 0.8 does not mean an 80% chance of a click. Separating similarity from calibrated probability avoids a common confusion when moving from retrieval to ranking.

2. Make features numerical

Suppose we describe one candidate with two toy features:

  • match: how strongly the available request history matches its topic, from 0 to 1.
  • fatigue: how often similar content has recently been shown, scaled from 0 to 1.

Real features require explicit definitions and query-time data. We invent these two numbers to expose the arithmetic. They are not measurements from Snap. Categorical inputs such as ad category can be represented using indicator columns or learned embedding lookups; a raw numeric ID should not imply an ordering.

3. Start with logistic regression

A linear model multiplies each feature by a coefficient and adds a bias:

z = bias + weight_match × match + weight_fatigue × fatigue
z = -2   + 3            × 0.7   - 2              × 0.2
z = -0.3

The coefficients say how inputs influence the raw score. The bias represents a baseline tendency when the other inputs are zero. The raw score z is called a logit; it can be any real number.

The sigmoid maps it to a number between zero and one:

p = sigmoid(z) = 1 / (1 + exp(-z))
p = sigmoid(-0.3) ≈ 0.426

Here exp is the exponential function. You can evaluate it with math.exp; you do not need to derive it before running the example. Larger logits produce larger probabilities, and z=0 produces p=0.5. See Google's logistic regression explanation.

This is logistic regression despite its name: a common binary classification model. Its output format can represent a probability, but the sigmoid alone does not guarantee empirically accurate probabilities. The data and training matter.

4. Learn from an outcome instead of writing the weights

Imagine that candidate was shown and clicked: label y=1. We want the model to assign the observed event a larger probability, on average across good training data. Binary cross-entropy, also called log loss, is:

loss = -[ y × log(p) + (1-y) × log(1-p) ]
if clicked:     loss = -log(p)
if not clicked: loss = -log(1-p)

At p≈0.426, a click gives loss about 0.854; a nonclick gives about 0.554. Confidently predicting near zero for an observed click incurs a large loss. The loss is averaged over examples so the model has to explain many outcomes, not just one convenient case.

For logistic regression with this loss, the derivative with respect to the logit is p-y. A derivative describes how a small score change affects the loss. At p≈0.426 with y=1, it is about -0.574. A simple gradient update subtracts learning-rate × derivative from the bias. With learning rate 0.5:

new_bias = -2 - 0.5 × (0.426 - 1) ≈ -1.713

With the same features, that increases the predicted click probability. For y=0 the update pushes it downward. A real optimizer updates all parameters using many batches; this one-bias step is an instructional example.

5. Where training rows come from

For an impression click model, a row describes what was shown and available before prediction; its label records whether a click occurred within the label definition. Unshown items have unknown outcomes. Training only on clicked rows would not teach an ordinary binary model what separates clicks from nonclicks.

There can be far more nonclicks than clicks. Class imbalance means the label frequencies differ substantially. Always predicting a nonclick can give high accuracy while offering useless ordering. Sampling nonclicks changes the training distribution; it can require corrections before scores are treated as probabilities under the serving distribution.

6. Good ordering and good probabilities differ

Suppose two models predict click probabilities for the same three ads:

model A: 0.03, 0.02, 0.01
model B: 0.30, 0.20, 0.10

Both produce the same ordering. Their implied number of clicks is very different. Calibration asks whether observed event frequencies match predictions among comparable groups. If items assigned roughly 0.1 probability click about 10% of the time under a well-defined exposure, that group is calibrated.

Discrimination metrics such as AUC focus on ordering positive examples above negative examples. Log loss evaluates probability assignments. Neither replaces examining calibration, slices, or online outcomes. A ranker used inside a value calculation can need both good ordering and accurate probabilities.

7. Pointwise, pairwise, and listwise training

Pointwise training predicts a target for each example, as in the click model above. Pairwise training compares two items for a query and encourages the preferred item to score higher. Listwise training considers a candidate list or its distribution jointly. These are families of objectives, not three model architectures.

You can train a neural network pointwise and still use it to rank by its output. The ranking task does not require that the loss literally sort items during training. Choosing an objective depends on labels, sampling, and the decision the product needs.

8. Why larger ranking models exist

A single linear coefficient cannot express every situation. “Hiking category” may be useful when paired with “recent hiking interest,” but less useful in other contexts. That dependency is a feature interaction.

Wide & Deep, DCN, DeepFM, and xDeepFM offer different ways to learn interactions. MMoE and PLE address a different axis: how several tasks, such as clicks and conversions, can share information without harming one another. They are not all successive replacements for the same problem.

These heavy models can consume the user and candidate together. Their output does not generally factor into one cached item vector and one query vector. That flexibility helps after retrieval has made the candidate count manageable. See the Snap reference learning path for all ten papers.

9. Ranking is followed by a product decision

Sorting by click probability optimizes a click proxy. A value objective might multiply a suitable per-impression conversion probability by a defined value. An auction then also has bids, budgets, pricing, and product constraints. A feed may re-rank for diversity or fatigue. The learned score is an input to selection, not a complete description of the selection system.

Implement the toy logistic predictor in ten lines using math.exp. Check z=0 gives p=0.5. Compute click and nonclick losses, then update the bias once with bias -= 0.5 * (p-y). Verify a positive example raises p and a negative lowers p.
