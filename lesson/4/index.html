Approximate nearest neighbors

Concept

Exact search scores every item and returns the largest scores. Approximate nearest neighbor search saves work by inspecting only promising regions or compressing representations. That introduces a speed/accuracy/memory tradeoff.

Flat search is exact. IVF groups vectors into coarse clusters and searches selected clusters. HNSW builds a navigable graph and explores promising neighbors. IVF's nprobe and HNSW's efSearch control search effort in different ways.

The index is a search structure

Your encoder defines the vectors and scores; an index organizes how to find high-scoring vectors. Think of a library: its catalog helps locate books but does not determine whether the books are good. Improving ANN cannot repair an encoder that learned irrelevant similarities.

Exact scoring work grows with item count times vector dimension. One million 64-dimensional float32 item vectors need about 256 million bytes for coordinates alone, before IDs, graph links, or other overhead. Search cost and memory matter alongside prediction quality.

IVF's clusters give a coarse map of where to look; HNSW navigates a graph. Their parameter values are not interchangeable units. “Approximate” means the search can miss exact neighbors, not that their scores become real relevance labels.

Worked example

Exact top-4 IDs are [3,7,2,9]. ANN returns [3,7,5,9]. Neighbor overlap is 3/4. If the user's actual held-out positive is item 7, both systems have target Recall@4 of 1 for that user. If it is item 2, exact succeeds and ANN fails. Approximation accuracy and recommendation quality answer different questions.

An IVF search probing one cluster may skip the cluster containing item 2. Probing more clusters can recover it at additional query cost. Searching every cluster in an IVFFlat index approaches exact scoring, though tie ordering can differ.

Application to this project

We export both towers' normalized vectors from one selected checkpoint and build indexes over the item vectors. On this small catalog, overhead can dominate. Performance numbers from a laptop and 1,447 items do not predict million-item latency. The reference exports storage size, not total resident or build-time memory.

Implement it

  1. Load the vector export and verify its model/embedding hashes.
  2. Build faiss.IndexFlatIP(d), add float32 item vectors, and search user vectors.
  3. Compare its top-K with a brute-force matrix product on a small fixture without ties.
  4. Build IVFFlat; train its coarse clusters before adding items. Sweep nprobe.
  5. Build HNSW and sweep efSearch; hold vectors and queries fixed.
  6. Warm up outside timing, measure p50/p95, and plot neighbor overlap versus latency.

Compare with src/ann.py and the ANN lab. Read Johnson/FAISS and HNSW; read ScaNN when adding quantization.
