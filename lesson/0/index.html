The retrieval funnel

Concept

A recommendation system cannot afford to run its most expensive model on every item. Retrieval uses a cheap score to find a manageable candidate set; ranking uses more features and computation to choose among those candidates. Eligibility determines which items can be shown at all. An auction can then combine predictions with bids and business rules.

Think of retrieval as deciding which applications reach an interview. A perfect interviewer cannot hire someone whose application was discarded earlier.

Start with one request

When Mira opens a feed, the system must fill a display opportunity. Its available inputs describe a user, a situation, and a catalog. “Useful” depends on the goal: a click, an enjoyable watch, and a purchase are different outcomes. Read the foundations if these terms are new.

Eligibility asks “may this item be shown?” Retrieval asks “which items merit more computation?” Ranking uses richer information to order or value that shortlist. Returning 500 candidates does not mean displaying 500 ads. Several retrieval sources can contribute items, and their raw scores can have different meanings. The ranker supplies a common comparison for the merged shortlist.

Recall and precision are different

Precision is the fraction of returned candidates that are relevant. Recall is the fraction of relevant items that were returned. A shortlist can tolerate some irrelevant candidates because ranking gets another chance to remove them. Dropping a valuable candidate is harder to repair.

Returning the whole catalog can give perfect coverage under a fixed label set while defeating the purpose of retrieval. The task is useful coverage within a candidate and latency budget, not maximizing one number without constraints.

Worked example

Suppose there are 1,000,000 eligible ads. A ranker takes 0.2 milliseconds per ad under an illustrative serial assumption. Scoring the entire catalog takes 200 seconds; scoring 500 candidates takes 100 milliseconds. Real systems batch and parallelize work, but the computation still has to fit a serving budget.

If there are 20 relevant ads and retrieval returns 15 of them in its 500 candidates, Recall@500 is 15/20 = 0.75. Ranking can reorder those 15; it cannot recover the five missing ads. The meaning of "relevant" must come from a defined label or evaluation proxy, not just whichever score the retriever produces.

Application to this project

MovieLens provides user/movie feedback, so movies are stand-ins for ads. We learn a cheap embedding score and evaluate whether a user's held-out positive survives candidate generation. We do not have bids, impressions, or real auction labels.

Snap's public post describes the funnel. Covington 2016 shows a separate candidate-generation and ranking design at YouTube. Our implementation is an educational design choice based on public retrieval research.

Implement it

Before training anything, make a list of 100 toy item IDs and a separate set of five relevant IDs. Write a candidate generator that returns ten items and a ranker that reorders those ten. Measure relevant-item coverage before and after ranking. Keep the same candidates while changing the ranking function.

Then draw the full funnel and label which component your code represents.

Self-check

  • Can a ranker repair candidate coverage while keeping the candidate set fixed?
  • Why is a retrieval latency reduction useful even if ranking quality is unchanged?
  • What information would you need to define relevance for ads rather than movies?
