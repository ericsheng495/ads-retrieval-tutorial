Embeddings & two towers

Concept

An embedding is a learned vector representation. A two-tower retriever maps a query/user through one function and an item through another. Their score is a dot product. Because the item function does not depend on the current query, we can compute item vectors in advance and search them at request time.

The representation is useful when relevant pairs have larger scores than other pairs. Its coordinates do not automatically have interpretable meanings such as "likes sports"; rotations of the entire space can preserve all dot products.

Vectors, IDs, and lookup tables

A vector is an ordered list of numbers; its dimension is the number of entries. For intuition, pretend two coordinates describe outdoor and gaming interests. Those invented meanings help explain arithmetic; learned coordinates need not have names. Training adjusts them to fit observed associations.

An ID is a label, not a quantity: user 200 is not twice as interested as user 100. An embedding lookup returns a trainable row for each known ID. Users with similar behavior can learn similar rows despite unrelated IDs. A feature encoder can instead compute a vector from metadata or history, allowing useful sharing when an entity has little data of its own.

Multiply and sum

The dot product of [a,b] and [c,d] is a*c + b*d. Each matching coordinate contributes to a compatibility score. A large score is relative to the learned task; 0.8 does not mean an 80% click probability. Each tower is simply a function producing one side's vector. Its name does not imply a particular number of layers.

Independence enables caching: compute one item vector per compatible model/item version, then compare it with many request vectors. A joint user/item scoring network, such as many heavy rankers, need not have this decomposition.

Worked example

A user vector is [1, 0]. Three unit item vectors are [1, 0], [0.6, 0.8], and [0, 1]. Dot products are 1, 0.6, and 0, so the first item is retrieved first.

Without normalization, item [3, 4] scores 3 with this user despite pointing in the same direction as [0.6, 0.8]. L2 normalization divides [3, 4] by its norm 5. With both sides normalized, the dot product equals cosine similarity and vector length no longer affects ordering. That discards a possible signal; it is a modeling decision, not a mathematical requirement for retrieval.

Application to this project

An ID embedding table returns one trainable row per known user/item. The reference adds a learned linear projection to each side and normalizes outputs. The towers are separate functions, but this ID-only linear model remains closely related to matrix factorization. Side features and history modeling arrive in lesson 6.

For batches of B users and B items with dimension d, encoder outputs have shape [B, d]. U @ V.T has shape [B, B]: each row scores one user against every item in that batch. Serving uses [B, d] @ [N, d].T for N catalog items.

Implement it

  1. Reproduce the three scores above using NumPy or PyTorch.
  2. Build nn.Embedding(n_users, d) and nn.Embedding(n_items, d).
  3. Add separate linear layers, then F.normalize(..., dim=-1).
  4. Check output shapes and norms before writing a loss.
  5. Cache all item outputs; verify cached and freshly encoded scores match.

Compare with src/model.py. Read DSSM for shared-space matching and Koren for the MF connection in the paper guide.
