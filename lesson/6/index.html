Features & user history

Concept

ID embeddings memorize behavior for known entities. Feature encoders can share information across entities: two movies may share genres even when one has few ratings. A history encoder maps a user's observed actions to a vector and can represent a user or session whose ID never appeared during training.

Pooling treats history as a set or bag. A sequence encoder can use order and recency. More complexity only helps if it adds useful information under a fair comparison.

What can generalize depends on the inputs

An ID-only encoder knows what training assigned to one identifier. Content features let it reuse relationships across similar items. A multi-hot genre vector has one position per genre and can mark several as active. An unknown identifier still needs a defined representation; a new random row is not knowledge.

Mean pooling averages history vectors. Attention pooling learns contributions from history elements. A sequence model can also represent position and temporal relationships. Start with the mean to find out what extra complexity contributes.

Every prediction needs a history cutoff. A padding mask excludes filler tokens; a causal mask restricts attention to earlier positions. Neither repairs a loader that already supplied future events. Input availability is a data-design concern.

Worked example

History item vectors are [1,0] and [0,1]. Mean pooling gives [0.5,0.5], which represents both interests equally. Weights 0.2 and 0.8 produce [0.2,0.8], emphasizing the second interest. Neither pooling rule distinguishes [A,B] from [B,A] unless the weighting mechanism uses position or time.

A sequence model with positional information can distinguish those orders. For a training target at time t, its input must stop before t. A causal attention mask prevents one position from seeing later positions, but cannot repair a data loader that already included the target in its history.

Application to this project

MovieLens genre flags can become a multi-hot content vector. An item tower might combine an ID embedding with a projection of genre features. A content-only path is needed for unseen items; concatenating an untrained new ID vector is not a cold-start solution. Track the original-to-contiguous item mapping when loading u.item; the baseline reference does not yet load genre features.

Implement it

  1. Extend data loading to preserve mappings and join genre flags to item IDs.
  2. Compare ID-only, genre-only, and ID+genre item towers.
  3. Replace user-ID lookup with a masked mean of pre-target training-history embeddings.
  4. Define padding and an empty-history fallback; test that padding does not alter pooling.
  5. Add learned pooling, then a causal sequence encoder with positions.
  6. Keep split, dimensions/budget, and evaluation policy comparable; report rare-item and heavy-user slices.

Read Airbnb embeddings and SASRec; PinSage is an optional graph extension. Record whether extra compute buys better recall instead of assuming it will.

Self-check

  • What does attention add if histories have no position or time signal?
  • Why must genre joins use a saved mapping rather than row order by assumption?
  • Can one user vector cover two unrelated interests without compromising retrieval?
