Evaluation you can trust

Concept

A split defines what information the model has and what future behavior it must predict. A candidate pool defines the alternatives it competes against. A metric only has meaning when both are stated. Strong baselines expose whether a complex model adds value beyond globally common items.

We use per-user training, validation, and test positives. Validation selects settings/checkpoints. Test estimates performance after selection; repeatedly choosing configurations based on test makes it part of model development.

Ask the evaluation question first

“Using only what was known then, can we retrieve the next positive among the allowed items?” The time cutoff defines inputs, labels define relevance, and the candidate pool defines competition. Changing any one changes the task.

If three of ten returned candidates are relevant, precision is 3/10. If those are all three relevant targets, recall is 3/3. Moving the best candidate from position ten to position one can leave Recall@10 unchanged, even though the display ordering improves. Position-sensitive metrics answer another question.

Why click AUC is different

AUC evaluates how often positive examples outrank negative examples under the chosen evaluation distribution. Good overall discrimination can coexist with missing an important item from a short top-K list. It also does not establish calibration: correct ordering and accurate event probabilities are separate.

Our one-target Recall@100 is an averaged hit indicator. It does not distinguish first from hundredth within that shortlist. That is intentional for a candidate coverage proxy, but it is not a complete measure of user experience.

Worked example

A user's four distinct positives arrive as A, B, C, D. Train on A/B, validate on C, test on D. During validation exclude A/B. During test exclude A/B/C. The held-out target remains eligible. An item can appear in another user's training data.

For three queries, top-2 predictions are [B,C], [A,D], [C,B] and targets are C,B,C. Two users have a hit, so one-target Recall@2 is 2/3. In this protocol it equals HitRate@2. With multiple relevant targets, recall needs a different denominator.

If a user has five eligible items, random Recall@2 is 2/5, not 2 divided by the original catalog size. Average this expectation across users when pool sizes differ.

Application: diagnose our measured first run

The saved five-epoch MovieLens reference has test Recall@100 of about 0.132, compared with 0.072 expected random and 0.274 popularity. Validation recall improved from about 0.087 at initialization to 0.144, while sampled training loss fell from about 0.609 in epoch 1 to 0.077 in epoch 5.

That supports learning relative to random, not superiority to popularity. Possible next hypotheses include the short schedule, weak ID-only representation, catalog sampling mismatch, and the positive-mass objective. None is established by this one experiment. See the measured output.

Implement it

  1. Hand-calculate the three-query example, then implement recall_at_k.
  2. Deduplicate user/item positives, split by per-user timestamp, and assert pair separation.
  3. Rank the full catalog, exclude seen items, and use deterministic tie handling.
  4. Compute popularity from training counts only; compare with expected random.
  5. Save validation metrics each epoch and evaluate the selected checkpoint on test.
  6. Add head/tail slices before changing the model. Compare with metrics.py.

Read the evaluation contract and Schnabel. Per-user chronology does not prevent cross-user future leakage; a separate global cutoff experiment is required for a deployment-like evaluation.
