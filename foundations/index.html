Start here: how recommendation systems work

You do not need a background in recommenders to start. Assume you can read a small Python function. We will define the ML vocabulary as it appears.

Our running example is Mira opening an app. The app can show a hiking-boot ad, a coffee subscription, or a mobile game. How should it decide? Every number in this example is invented for learning, not a claim about a real platform.

1. What is the system trying to decide?

A recommendation is a choice about what to show someone. A request is one occasion when the app needs that choice. An item is anything that could be shown: a video, product, movie, or ad. The catalog is the collection of items.

There is no universal definition of the “best” item. You must choose an objective, meaning the outcome you want to improve. A movie service might care about enjoyable viewing; an advertiser might care about purchases. A click is easier to observe, but more clicks need not mean more satisfaction or purchases.

The request usually includes context: time, device, surface, recent activity, and other available information. Mira may want a quick coffee offer during a commute and hiking equipment while planning a trip. Personalization can change with the request even for the same person.

Search and recommendation overlap. Search supplies an explicit query; a home feed often has to infer intent from context and history. Neither task requires that the first model you build be a neural network.

2. What evidence does the system have?

A feature is an input known when making a prediction. A label is the outcome we later use to judge that prediction. A training example pairs inputs with an observed label.

Moment What we know Role
Before showing an ad Mira's earlier activity, ad category, current time Features
When an ad is displayed Which ad appeared, where, and under which model Impression log
After display Whether a click or qualifying purchase occurred Possible labels

An impression is a recorded display opportunity under the product's logging definition. A click is one interaction. A conversion is a defined outcome, such as an app install or purchase, with a specified attribution/window rule. They are different events. Some purchases follow no recorded click.

For a click model, a training row might be:

features: user=Mira, category=hiking, previous_hiking_views=3, hour=18
label: clicked=1

clicked=1 is a label, not an input available before the impression. Accidentally using it as an input is leakage: the model gets information from the answer.

An explicit rating such as five stars asks for a stated preference. An implicit signal such as a click infers preference from behavior. A missing click on a shown ad is an observed nonclick under that exposure. A missing click on an ad Mira never saw is an unknown outcome, not proof of dislike.

3. Start with recommendations you can explain

A baseline is a simple approach you can compare against. Returning popular items is a useful baseline: rank by historical interaction count and exclude ineligible items. It provides useful suggestions even before personalizing. Its weakness is giving the same ordering to people with different interests.

Content-based recommendation uses item descriptions. If Mira likes hiking content, hiking-gear features may help find other items she would like. Collaborative filtering learns from patterns across people's interactions: Mira's history overlaps with Alex's, so an item Alex enjoyed can be a candidate for Mira even without similar descriptions. These approaches can be combined. See Google's introductions to content-based and collaborative filtering.

Consider this deliberately tiny interaction table:

Person Hiking boots Trail guide Coffee offer
Mira clicked clicked unknown
Alex clicked clicked clicked
Jo unknown unknown clicked

Collaborative patterns can suggest the coffee offer to Mira. They do not prove she will like it. The table is sparse: most real user/item outcomes are unknown. Patterns can also reflect what the earlier system chose to display.

4. Why there are several models in one request

With three items, scoring every item is easy. With millions, an expensive model for every possible pair can exceed the response-time budget. A staged system spends cheap computation broadly and expensive computation on a smaller set.

  1. Eligibility: remove items that cannot be shown under current rules.
  2. Retrieval / candidate generation: find a manageable shortlist with cheap scores.
  3. Ranking: use richer information to score the remaining candidates.
  4. Final selection: apply product rules or an auction to choose what appears.
  5. Feedback: log what was shown and what happened, creating future training data.

Different candidate generators may contribute popular items, semantic matches, or content matches. Their scores need not mean the same thing. A later ranker can give the merged shortlist a common score. The word “ranking” can describe the overall ordering task or the specific heavy-scoring stage; read it in context.

5. A score is a statement about a task

Suppose our invented model predicts these probabilities per impression:

Ad Probability of click Probability of conversion Value per conversion
Hiking boots 0.06 0.01 5 units
Coffee offer 0.04 0.02 3 units
Mobile game 0.12 0.004 4 units

Maximizing predicted clicks selects the game. Maximizing predicted conversions selects coffee. Multiplying conversion probability by the illustrative value gives 0.05, 0.06, and 0.016 units per impression; coffee wins again. A probability of 0.02 means two expected events per 100 comparable opportunities, not a promise that exactly two will occur.

These are unconditional per-impression conversion probabilities. If you instead have a conversion probability given a click, you need to account for the click event before treating it as an expected outcome per impression. Keep the conditioning and attribution definitions consistent.

Real auctions include constraints and pricing rules. Our value multiplication is a teaching objective, not a description of Snap's auction formula.

6. Training and serving are different activities

During training, the system adjusts model parameters using historical examples. A parameter is a learned number such as a coefficient or an embedding coordinate. A loss measures how badly predictions disagree with the training target. An optimizer changes parameters to reduce the loss.

During serving / inference, the model uses its current parameters on a new request. It cannot look at the future click. Training is like practicing with answered exercises; inference is answering the next question with what you learned.

Training can run on a schedule while serving continues. Item representations can be precomputed; user/request representations may need to be computed when the request arrives. These are engineering choices with freshness and cost tradeoffs.

7. Why testing on the future matters

A model can memorize earlier examples without improving new decisions. Training data teaches it; validation data helps choose settings; a reserved test period checks the result after those choices. Repeatedly choosing based on test results turns that test into more development data.

An offline metric asks a limited question about a fixed dataset. An online A/B experiment compares actual outcomes under two policies. In a marketplace, one group may change the inventory or budgets available to another. Later lessons explain why randomizing users alone does not automatically solve that problem.

8. What this project teaches first

We start with retrieval on MovieLens: user/movie positive pairs, independently encoded vectors, and a shortlist metric. Movie ratings do not provide ad impressions, bids, or conversion labels. The ranking primer teaches how a scoring model works before the model architecture lessons. Then return to lesson 0 to build the retrieval loop.
