Batch, offline, and online training: the ML platform view

The model architecture is only one part of a production recommender. A platform must turn events into reproducible examples, train efficiently, validate the result, and deploy compatible artifacts while the product keeps serving. Start with the two-stage system if those artifacts are still unclear.

1. Batch and offline are not opposites

“Batch” describes several different things. Ask which meaning someone intends.

Term What it describes Example
Mini-batch training Examples processed together for a forward/backward computation 256 user/item examples at a time
Full-batch gradient descent An update computed using the whole training dataset One update from all N examples
Batch/offline training job A bounded run over stored data, outside the serving request A nightly job training on a fixed snapshot
Micro-batch stream processing A small time slice or chunk of arriving events Materialize new examples every few minutes
Online/incremental learning Updating a model state from newly arriving data Continue learning from recent mature labels
Batch inference Predicting for many inputs without learning Export item embeddings for an ANN index
Online inference Predicting during a live request Encode the user and rank current candidates

A nightly offline job normally trains with mini-batches. A near-real-time learner can buffer examples into mini-batches too. A model serving online does not necessarily learn online. Computing a million item embeddings changes outputs and index contents, not model weights.

“Offline” also appears in offline evaluation, which means testing on a stored dataset rather than measuring actual deployed outcomes. That is another axis, not a synonym for training.

2. Three independent choices

Separate when the job runs, what data it reads, and where its weights start. A job can run hourly but still retrain from scratch. Another daily job can warm-start from yesterday's weights and process only new data. A streaming learner can use a replay buffer of older examples alongside fresh ones.

Choice Simpler operational benefit Main complication
Full retraining on a versioned window Clear reset and repeatable experiment Data/compute cost and deployment lag
Warm-start on recent + historical data Reuses useful learned state Dependence on the predecessor checkpoint and replay policy
Incremental updates on arriving examples Potentially faster adaptation Ordering, duplicates, late labels, forgetting, recovery

A possible teaching design combines periodic full retraining, more frequent incremental jobs, and fresh request-time features. These mechanisms address different kinds of freshness; it is not a claim about a particular Snap team.

3. The actual platform pipeline

Think of each box as an artifact contract, not necessarily one service. An orchestrator schedules dependencies, retries failures, tracks resources, and records which outputs belong to which run. The training script should not silently read a moving “latest” dataset while claiming reproducible results.

For one run, record the data snapshot/window, label definition and maturity cutoff, feature schema/transforms, sampling policy, code/environment, predecessor checkpoint if any, and training configuration. The output is a validated model plus dependencies, not just model.pt.

4. Labels have a clock; features have another clock

Suppose an impression occurs at time T and a conversion can count for 48 hours. At T+1 hour, “no conversion yet” is not a mature negative. A simple training policy waits for the observation window, with an explicit allowance for reporting delay. Other approaches model censoring/delay, but need their own assumptions.

Feature event time says when a value describes the world. Availability or ingestion time says when the platform could actually use it. A backfilled feature can have an old event timestamp while becoming available much later. Training should not use a later correction as though the serving model knew it.

Example: a purchase happened at 10:00, but the feature service received it at 10:20. A 10:05 prediction could not have used that purchase count, even though the event itself was earlier. Reconstruct both timing constraints when they matter. Feast's point-in-time join documentation explains the distinction and its created-timestamp filtering option; support depends on the offline store.

5. Feature consistency across training and serving

An offline table and a low-latency feature store can represent the same conceptual feature with different freshness and transformation paths. Training-serving skew occurs when the model learns from inputs different from those it receives.

Write an exact contract: entity key, event-time meaning, availability rule, aggregation window, missing-value default, vocabulary version, and numeric scale. “Seven-day interaction count” is ambiguous without cutoff, deduplication, and late-event rules. Reuse transformations where practical and test historical reconstruction against captured serving inputs.

Fresh features do not require freshly trained weights on every request. A fixed user encoder can immediately respond to a new history feature if its input and serving path support that update. The index's item content may still be older; measure those freshness dimensions separately.

6. Mini-batches, accumulation, and the effective update batch

In ordinary synchronized data-parallel training, suppose each of W workers processes B examples per micro-step and accumulates A micro-steps before updating:

examples contributing to an optimizer update = B × W × A

For B=128, W=4, and A=4, that is 2,048 examples per update, assuming the inputs are distinct and loss scaling is correct. Accumulation trades additional work between optimizer steps for lower per-micro-step activation memory. It does not make all examples simultaneously available to every operation.

For in-batch retrieval loss, a worker may still see only B candidate columns in that forward pass. Gathering candidates across W workers can expose B×W columns. Accumulating A steps does not automatically create a B×W×A candidate pool. A queue or a different computation would be required, with gradient and staleness choices to define. Thus matching an “effective batch size” does not establish equivalence of two contrastive-training setups.

Even for other losses, normalization layers, randomness, variable-size batches, and learning-rate schedules can change equivalence. PyTorch's accumulation examples document effective-step scaling and mixed-precision handling.

7. Distributed training is a correctness problem too

Data parallelism replicates a model across workers and combines gradients. PyTorch DDP synchronizes gradients; the application still needs appropriately partitioned examples. Giving every worker identical data wastes diversity and can change a retrieval sampler's assumptions. See the DDP design notes.

For an illustrative two-worker task, worker A has 100 valid labels and worker B has 10. Blindly averaging their locally averaged losses gives the workers equal influence, not the 110 examples equal influence. Decide on the global normalization and valid-label masks, particularly with sparse multi-task conversion labels.

For retrieval, also specify local versus cross-worker negatives, duplicate-item masking, whether gathered representations preserve the intended gradient paths, and the exact sampling distribution. All-gathered candidates can grow the score matrix and communication substantially.

Model parallelism/sharding distributes parameters, such as large embedding tables, across devices. It solves a different problem from replicating a small model for throughput. Sparse lookups, optimizer-state memory, and inter-device traffic can dominate a recommender even when its dense network is modest.

Synchronous updates coordinate workers before applying a step; asynchronous updates can reduce waiting but introduce stale-update and ordering considerations. Neither is universally better. Record the actual setup when comparing results.

8. Where throughput gets lost

Profile the whole path: read/decompress records → join or fetch features → build batches → transfer data → embedding lookup → dense computation → communicate gradients/representations → optimizer update → checkpoint. Adding GPUs does not repair an input pipeline that cannot feed one GPU.

Track examples/second, time spent waiting for data, communication time, memory, checkpoint overhead, job completion time, and cost to reach a chosen validation quality. A high hardware-utilization number by itself is not a useful business or model-quality result.

Learning-rate schedules can be tied to optimizer steps, examples, or epochs. Changing batch size changes the relationship among those units. The same number of epochs with a new batch size is not automatically the same optimization budget.

9. Freshness is an end-to-end budget

For a simplified sequential pipeline, event-to-serving delay includes label wait, scheduling wait, example preparation, training, export/index construction, and deployment. Some real steps overlap; write down what your measurement includes.

An invented example: 48-hour label window + 12-hour average scheduling wait + 1-hour preparation + 2-hour training + 0.5-hour indexing + 0.5-hour deployment is about 64 hours. The 12-hour average assumes uniform arrivals with a daily schedule. Reducing training by ten minutes cannot remove a two-day label window.

Measure feature freshness, latest included mature event time, model age, item index age, and deployment lag separately. “We retrain hourly” does not imply hour-old learning signals. A fast update with broken labels is not an improvement.

10. Recovery, retries, and reproducibility

A resumable training checkpoint can require optimizer/scheduler state, current step, mixed-precision scaler state where used, sampler/cursor or stream offsets, random state, and data/code versions in addition to model weights. PyTorch's checkpoint guide explains saving training state beyond weights. Exact replay across distributed systems and changing hardware can require further controls.

The tutorial's src/train.py saves selected model weights and export metadata; it does not yet implement an exact-resume distributed training checkpoint. That distinction is intentional and should remain visible in an experiment note.

Retries must not overwrite another run's artifacts or silently advance a stream cursor without its associated learning state. Use immutable output versions, explicit input IDs/offsets, and validated publication steps. Define whether reprocessing duplicates is possible rather than claiming “exactly once” from the existence of a retry button.

11. A trained model is not yet a serving release

For two-tower retrieval, an export may change both query and item encoders. Build compatible item vectors and indexes, validate them, then promote a serving bundle with a clear compatibility rule. A feature-only eligibility change may have a different update path. Ranking weights, retrieval weights, vocabulary, feature transforms, and index parameters each need versions and owners.

Check offline quality/slices, score calibration where relevant, artifact integrity, serving correctness, latency, memory, and fallbacks before exposure. A registry tracks candidate versions; a rollout policy controls who receives them. Updating a registry entry is not itself a successful deployment.

A pipeline framework such as TFX illustrates the separation among ingestion, validation, transforms, training, evaluation, and serving checks. These responsibilities exist even if you choose other tools.

12. Monitoring after rollout

Use fast operational signals such as error rate, latency, missing features, unknown IDs, score distributions, index freshness, and eligible fill rate. Use mature outcome data for delayed quality and calibration checks. A missing conversion feed should not masquerade as a sudden model-quality collapse.

Trace a request to the deployed model/index/features and an artifact back to its training run. Rollback must restore a compatible bundle, not arbitrarily pair yesterday's query tower with today's index. A canary or shadow run helps observe behavior but does not replace an appropriate causal experiment.

13. A small platform exercise, without a cluster

  1. Write a training-run manifest naming the dataset cutoff, label window, feature schema, sampler, starting checkpoint, and output versions.
  2. Simulate daily full retraining versus hourly incremental updates with explicit example windows. Identify which data is replayed and why.
  3. Add optimizer/step state to a scratch training checkpoint; interrupt and resume on fixed data, documenting any differences.
  4. Compare local batch size and accumulation in the interactive example. Explain why the retrieval candidate pool did not multiply with accumulation.
  5. Build a compatible model/index export, then deliberately mix versions and verify rejection. Sketch rollback and a delayed-label monitoring fault.

The goal is to reason about contracts, cost, freshness, and failure modes before introducing orchestration or distributed infrastructure. Return to production and transfer or the Snap post companion to connect these ideas to the rest of the course.
